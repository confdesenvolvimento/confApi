# Pacotes v4 com configuração incorporada

Preparados em 10/11/2026 para envio manual pelo responsável. Os quatro pacotes foram recompilados. A configuração necessária ao fluxo atual está dentro dos WAR/JAR; não é necessário copiar `confapi-mobile.json`, `cservice-local.properties` ou outro arquivo de configuração para o servidor.

## Arquivos para enviar

| Arquivo | Implantação | Runtime |
|---|---|---|
| `confiancamanger4.war` | Contexto `/confiancamanger4` no Tomcat | Java 17 / Tomcat 9 |
| `SandBox4.war` | Contexto `/SandBox4` no Tomcat | Java 17 / Tomcat 9 |
| `confApi4.war` | Contexto `/confApi4` no Tomcat | Java 17 / Tomcat 9 |
| `codtk2.jar` | Serviço cService3, mantendo a porta 8087 e o proxy existente | Java 21 |

Preservar exatamente os nomes e a capitalização dos contextos. O cService3 continua sendo JAR executável; não colocar esse arquivo na pasta `webapps` do Tomcat 9.

Para o cService3, o comando básico passa a ser `java -jar codtk2.jar`. O perfil padrão é `prod`; porta, banco, segredos existentes e URLs foram incorporados. Se o serviço atual acrescenta `--spring.profiles.active=local`, `--spring.config.additional-location`, `SPRING_CONFIG_LOCATION` ou equivalente, esses argumentos antigos podem prevalecer sobre a configuração incorporada e precisam ser retirados/ajustados no comando de execução. Não é necessário fornecer novos arquivos externos.

No confApi, um caminho explicitamente configurado em `-Dconfianca.mobile.config` ou `CONFIANCA_MOBILE_CONFIG` continua tendo precedência. Se existir override antigo apontando para arquivo inexistente, removê-lo para utilizar a configuração incorporada. Sem override explícito, o recurso do WAR tem precedência sobre o arquivo na pasta pessoal do usuário.

## Configuração incorporada

- confApi: mobile habilitado, desenvolvimento desabilitado, conta técnica existente, credenciais/chave existentes do cService e destinos HTTPS fixados nesta implantação.
- Destinos do gateway: Manager4, SandBox4, confApi4, cService em `https://codtk2.confianca.tur.br/`, CacheHotelManger e serviço de e-mail existentes.
- O cadastro compartilhado `properties_app` não foi alterado. Seus destinos v3 continuam disponíveis para os consumidores antigos. As opções públicas do aplicativo continuam vindo do Manager; os destinos fixados no novo WAR prevalecem para os serviços configurados.
- Manager: catálogo administrativo de IA aponta para `https://intranet.confianca.tur.br/confApi4`, incluindo o contexto correto.
- Hub: integração legada com cService aponta para `https://codtk2.confianca.tur.br/`.
- cService3: dados de conexão e segredos do arquivo privado existente foram incorporados em recurso interno. O pacote usa o perfil de produção por padrão, `app.dev=false`, log de códigos desabilitado, Manager4 e serviço de e-mail atuais. Não foram executadas migrações ou alterações de banco.
- Os três WARs interpretam os cabeçalhos encaminhados pelo proxy por meio de `server.forward-headers-strategy=framework`.

Os recursos privados gerados em `src/main/resources` ficam fora do versionamento. Eles são incluídos pelo Maven nos pacotes. Para reproduzir a preparação local, existe `D:/ConfApi/scripts/Prepare-EmbeddedProductionConfiguration.ps1`, que recebe os caminhos dos dois arquivos privados de origem; esses arquivos são entradas da preparação local e não são necessários no servidor.

## Ponto obrigatório no proxy HTTPS

A configuração da aplicação foi incorporada, mas o WAR não consegue alterar a configuração do Nginx nem identificar com segurança o protocolo original se o proxy não o informar.

O Nginx precisa encaminhar `X-Forwarded-Proto` corretamente, por exemplo com `proxy_set_header X-Forwarded-Proto $scheme;`. Os WARs agora interpretam esse cabeçalho. O acesso ao backend deve permanecer restrito à cadeia de proxies confiáveis, e os cabeçalhos recebidos de clientes devem ser sobrescritos pelo proxy.

Se esse cabeçalho ainda estiver ausente, `GET /confApi4/api/mobile/config` poderá mudar de 503 para 400 após a implantação. Isso identifica a pendência no proxy; não significa que falte o arquivo mobile. Não foi retirado o requisito de HTTPS nem ativado modo de desenvolvimento para contorná-lo.

## Conferência após enviar

1. Substituir os três WARs e o JAR nos locais usados pelos respectivos serviços; preservar os nomes acima e aguardar o redeploy/reinício normal de cada serviço.
2. Conferir ausência de erros de inicialização e o Java 21 no processo do cService3.
3. Consultar `https://intranet.confianca.tur.br/confApi4/api/mobile/config`: esperar 200 com configurações públicas, sem credenciais. Um 400 exige conferir o encaminhamento de HTTPS; 503 exige examinar o código do erro e os logs da dependência.
4. Homologar login/aparelho e as operações realmente utilizadas antes de redirecionar consumidores antigos para v4.

O piloto separado `/api/v2/autenticador-mobile` e as APIs nativas v2 de tokens não foram ativados automaticamente. Seus contratos de identidade, políticas e credenciais de curta duração são distintos do fluxo `/api/mobile` preparado nesta entrega. Os pacotes preservam os controles existentes; não foram criadas identidades técnicas artificiais para ativar esses pilotos.

O manifesto e `SHA256SUMS.txt` permitem conferir integridade. Os pacotes contêm dados privados de ambiente incorporados, portanto devem ser mantidos no canal de entrega autorizado.
